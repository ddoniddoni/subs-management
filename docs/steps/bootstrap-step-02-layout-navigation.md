# 실행 계획 - Bootstrap Step 02 레이아웃 및 내비게이션 구성

## 목적

Step 01에서 만든 라우트 골격 위에 고객용과 관리자용 공통 레이아웃을 붙여, 개별 페이지 목록이 아니라 실제 앱 구조처럼 보이기 시작하는 기반을 만든다.

## 이번 단계에서 할 일

- 고객용 공통 레이아웃 구성
- 관리자용 공통 레이아웃 구성
- 고객용 주요 이동 링크 추가
- 관리자용 주요 이동 링크 추가
- 페이지 제목과 설명을 공통 패턴으로 정리할 수 있는 페이지 헤더 컴포넌트 추가
- Step 01 플레이스홀더 페이지를 새 레이아웃 위에 배치

## 이번 단계에서 하지 않을 일

- 실제 고객 데이터, 결제 데이터, 환불 데이터 연결
- 고급 테이블, 필터, 차트 UI 구현
- 관리자 권한 제어 로직 구현
- 인터랙티브 폼과 모달 구현
- 테스트 환경 확장

## 구현 방향

### 1. 고객용 레이아웃
- 가벼운 상단 내비게이션을 둔다.
- 브랜드 제목과 핵심 고객용 링크를 제공한다.
- 마케팅 과잉 없이 제품 구조가 드러나는 형태로 유지한다.

### 2. 관리자용 레이아웃
- 사이드바 또는 고정 내비게이션을 둔다.
- 운영 섹션 이동이 한눈에 보이게 한다.
- 콘텐츠 영역은 이후 테이블과 대시보드가 들어와도 확장 가능한 구조로 잡는다.

### 3. 공통 페이지 헤더
- 페이지 제목과 설명을 공통된 패턴으로 렌더링한다.
- 이후 액션 버튼이나 보조 메타 정보를 붙이기 쉬운 구조로 만든다.

### 4. 기존 페이지 정리
- Step 01에서 만든 플레이스홀더 문구를 새 레이아웃 구조에 맞게 조정한다.
- 각 라우트가 소속된 영역이 레이아웃만 봐도 드러나게 만든다.

## 구현 원칙

- 아직은 컴포넌트를 과하게 세분화하지 않는다.
- 고객용과 관리자용의 정보 구조 차이를 분명하게 보여준다.
- 라우트 그룹이나 레이아웃 파일을 활용해 중복을 줄인다.
- 이후 Step 03 UI 프리미티브 작업과 충돌하지 않게 단순한 구조로 시작한다.

## 리스크

### 리스크 1
지금 레이아웃을 너무 화려하게 만들면 이후 공통 UI 작업과 충돌할 수 있다.

대응:
- 구조와 내비게이션에 집중하고, 시각적 디테일은 최소화한다.

### 리스크 2
고객용과 관리자용 레이아웃 경계가 어중간해질 수 있다.

대응:
- 내비게이션 방식, 공간 구성, 문구 톤을 명확히 구분한다.

### 리스크 3
페이지 헤더 패턴을 너무 일찍 과설계할 수 있다.

대응:
- 제목과 설명 중심의 얇은 컴포넌트로 시작한다.

## 완료 기준

- 고객용 공통 레이아웃이 적용된다.
- 관리자용 공통 레이아웃이 적용된다.
- 각 영역에서 주요 페이지 이동이 가능하다.
- 최소 1개의 공통 페이지 헤더 컴포넌트가 도입된다.
- 기존 Step 01 페이지가 새 레이아웃 위에서 정상 렌더링된다.
- `npm run lint`
- `npm run typecheck`
- `npm run build`
