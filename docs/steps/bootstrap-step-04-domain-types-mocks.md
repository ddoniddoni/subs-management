# 실행 계획 - Bootstrap Step 04 도메인 타입 및 목업 데이터 구성

## 목적

Step 03에서 만든 공통 UI 프리미티브 위에, 실제 구독 제품처럼 보이기 위한 핵심 도메인 타입과 목업 데이터를 추가한다.

## 이번 단계에서 할 일

- `customer`
- `plan`
- `subscription`
- `payment`
- `invoice`
- `refund`
- `coupon`
- `admin user`
- `role`
- `audit event`
- `metric snapshot`

위 항목에 대한 타입을 정의한다.

- 상태값과 라벨을 중앙 관리할 수 있는 상수 또는 enum 구조를 추가한다.
- `src/mocks/`에 화면에서 재사용할 수 있는 목업 데이터를 구성한다.
- 최소 1개 이상의 고객용 화면과 2개 이상의 관리자용 화면에서 목업 데이터를 실제로 사용한다.
- Step 03에서 만든 `StatCard`, `StatusBadge`, `TableShell`이 도메인 데이터와 연결되도록 정리한다.

## 이번 단계에서 하지 않을 일

- 실제 API 연동
- 실제 인증 / 권한 검사
- 복잡한 폼 제출 로직
- 환불 승인, 결제 재시도 같은 실제 액션 처리
- 테스트 환경 확장

## 대상 구조

### 타입 위치
- `src/types/` 또는 기능별로 필요한 경우 `src/features/*` 내부 타입 파일

### 목업 데이터 위치
- `src/mocks/`

### 우선 연결 대상 화면
- 고객용
  - `/app/subscription`
  - `/app/billing`
- 관리자용
  - `/admin`
  - `/admin/customers`
  - `/admin/payments` 또는 `/admin/refunds`

## 구현 방향

### 1. 도메인 기준 통일
- 문자열 상태값을 페이지마다 직접 쓰지 않는다.
- 상태 표시와 테이블 표시에서 같은 타입과 라벨 맵을 재사용한다.

### 2. 목업 데이터 품질
- 단순한 happy path만 두지 않는다.
- 결제 실패, 환불 대기, 해지 예정, 쿠폰 적용, 권한 차이, 감사 이벤트 같은 운영 시나리오를 포함한다.

### 3. 화면 적용 방식
- 기존 플레이스홀더 데이터를 제거하고, 실제 도메인 목업을 기반으로 카드/배지/테이블을 구성한다.
- 고객 화면보다 관리자 화면이 더 다양한 상태를 보여주도록 한다.

### 4. 확장성
- 다음 단계에서 필터, 상세 페이지, 액션 흐름을 붙이기 쉽도록 엔티티 간 관계를 자연스럽게 구성한다.

## 구현 원칙

- 타입은 엄격하게 유지한다.
- `any`는 사용하지 않는다.
- 목업 데이터는 화면 데모용이 아니라 실제 제품 흐름을 설명할 수 있어야 한다.
- 도메인 상수와 표시 라벨은 분리 가능하게 설계한다.

## 리스크

### 리스크 1
목업 데이터가 너무 얕으면 이후 관리자 워크플로우 설득력이 떨어질 수 있다.

대응:
- 실패 케이스와 예외 상태를 처음부터 포함한다.

### 리스크 2
타입과 목업 파일이 한곳에 과하게 몰릴 수 있다.

대응:
- 공통 타입과 기능별 파생 타입을 구분하고, 필요한 경우 기능 폴더로 나눈다.

### 리스크 3
표시용 라벨과 내부 상태값이 뒤섞일 수 있다.

대응:
- 내부 상태값은 코드 친화적으로 두고, 화면용 라벨 매핑은 별도 상수로 관리한다.

## 완료 기준

- 핵심 도메인 타입이 추가된다.
- 핵심 목업 데이터가 추가된다.
- 고객용 1개 이상, 관리자용 2개 이상 화면이 실제 목업 데이터를 사용한다.
- 상태 배지와 통계 카드가 하드코딩 문구 대신 도메인 데이터 기반으로 표시된다.
- `npm run lint`
- `npm run typecheck`
- `npm run build`
