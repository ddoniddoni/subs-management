# 실행 계획 - Bootstrap Step 13 관리자 권한 / 접근 제어

## 목적

Step 12에서 분석 대시보드까지 채웠으니, 이번 단계에서는 운영 콘솔의 신뢰도를 높이는 관리자 권한 흐름을 만든다. 운영자마다 볼 수 있는 화면과 처리 가능한 업무가 다르다는 전제를 반영해서 `/admin/admin-users`를 실제 권한 운영 화면으로 바꾸고, 레이아웃 수준에서 접근 가능한 메뉴와 화면을 역할 기반으로 제어한다.

## 이번 단계에서 할 일

- `/admin/admin-users` 플레이스홀더 제거
- 관리자 역할 / 권한 / 라우트 정책 helper 추가
- 운영자 검색 / 필터 / 정렬 / 페이지네이션 테이블 구현
- 역할별 권한 요약 카드와 라우트 접근 매트릭스 구현
- 관리자 레이아웃 권한 가드 및 모의 세션 전환 UI 추가
- 관련 테스트 추가

## 이번 단계에서 하지 않을 일

- 실제 로그인 / 세션 / OAuth 연동
- 서버 단 권한 검증
- 세분화된 action-level permission editor
- 관리자 초대 / 삭제 / 비밀번호 재설정

## 우선 대상 화면

### 1. `/admin/admin-users`
- 운영자 현황 요약
- 역할별 권한 카드
- 운영자 디렉터리 테이블
- 라우트 접근 매트릭스

### 2. 관리자 레이아웃
- 역할 기반 네비게이션 노출
- 접근 불가 화면 차단 메시지
- 상단 운영자 세션 전환 UI

## 구현 방향

### 1. 권한 정책 중앙화
- 역할별 권한과 허용 라우트를 helper 한 곳에서 관리해 다른 관리자 화면도 같은 규칙을 재사용할 수 있게 한다.

### 2. 운영 흐름 중심 화면
- 단순 역할 목록이 아니라 "누가 어떤 화면에 접근 가능한지", "최근 어떤 업무를 했는지"를 같이 보여준다.

### 3. 목업 세션 기반 접근 제어
- 실제 인증 연동 전 단계이므로 운영자 전환은 상단 mock session UI로 처리하고, 그 결과를 레이아웃 가드와 메뉴 필터링에 연결한다.

### 4. 테스트로 권한 규칙 고정
- 민감한 규칙은 helper 테스트와 가드 렌더링 테스트로 고정해 이후 단계에서 회귀를 막는다.

## 리스크

### 리스크 1
프론트엔드 가드만으로 실제 접근 제어처럼 과신될 수 있다.

대응
- mock session 기반이라는 설명과 차단 메시지를 UI에 직접 노출한다.

### 리스크 2
역할 정책이 늘어나면 조건문이 빠르게 복잡해질 수 있다.

대응
- 라우트 정책 배열과 역할 메타 정보를 별도 helper로 분리한다.

### 리스크 3
운영자 데이터가 적어도 테이블 인터랙션이 과해 보일 수 있다.

대응
- 이후 실제 관리자 데이터 확장을 고려한 기본 골격으로만 넣고, 과한 폼 편집은 다음 단계로 미룬다.

## 완료 기준

- `/admin/admin-users`가 실제 운영 권한 화면으로 동작한다.
- 관리자 레이아웃이 역할별 네비게이션과 접근 차단 메시지를 제공한다.
- 운영자 검색 / 필터 / 정렬 / 페이지네이션이 동작한다.
- 관련 테스트가 추가되고 통과한다.
- `npm.cmd run lint`
- `npm.cmd run typecheck`
- `npm.cmd run test`
- `npm.cmd run build`
