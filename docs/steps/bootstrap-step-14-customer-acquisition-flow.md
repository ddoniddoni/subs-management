# 실행 계획 - Bootstrap Step 14 고객 획득 흐름

## 목적

지금까지는 관리자 콘솔 쪽이 중심이었고, 고객용 앱은 구조만 잡혀 있었습니다. 이번 단계에서는 제품이 실제 서비스처럼 보이도록 고객이 처음 만나는 세 화면, 즉 랜딩, 요금제, 체크아웃 흐름을 완성해 고객 획득 경험을 붙입니다.

## 이번 단계에서 할 일

- `/` 랜딩 페이지 구현
- `/pricing` 요금제 비교 화면 구현
- `/checkout` mock checkout 흐름 구현
- 고객 획득용 helper / 파생 데이터 모듈 추가
- 관련 테스트 추가

## 이번 단계에서 하지 않을 일

- 실제 회원가입 / 인증
- 외부 결제 게이트웨이 연동
- 구독 변경 / 해지 같은 사후 관리 기능 확장
- 결제 영수증 다운로드

## 우선 대상 화면

### 1. `/`
- hero
- 제품 가치 제안
- 운영 신뢰 포인트
- 추천 플랜 미리보기
- FAQ

### 2. `/pricing`
- billing interval 전환
- 플랜 카드
- 기능 비교표
- checkout 이동 CTA

### 3. `/checkout`
- 선택 플랜 요약
- 고객 정보 폼
- 주문 요약
- coupon preview
- loading / success / error 상태

## 구현 방향

### 1. 마케팅과 운영 톤 연결
- 고객용 화면도 결국 운영 콘솔과 이어지는 제품이므로, "안정적인 구독 운영"이라는 메시지를 계속 유지한다.

### 2. 계산 로직과 UI 분리
- 가격 계산, 할인 계산, 플랜 강조 같은 로직은 helper에 두고 UI는 렌더링과 상호작용에 집중한다.

### 3. 실제 전환 흐름처럼 보이는 checkout
- 단순 placeholder가 아니라 입력, 검증, 제출, 결과 상태가 모두 보이는 mock checkout으로 만든다.

### 4. 테스트로 핵심 흐름 고정
- interval 전환, 주문 요약 계산, 제출 성공 상태 같은 핵심 동작을 테스트로 남긴다.

## 리스크

### 리스크 1
고객용 화면이 데모성 랜딩처럼만 보일 수 있다.

대응
- 운영 신뢰, 결제 안정성, 환불 대응 같은 실제 서비스 메시지를 중심으로 카피를 구성한다.

### 리스크 2
checkout 상태가 많아지면 컴포넌트가 커질 수 있다.

대응
- 상태 계산과 표시 데이터를 helper와 작은 section으로 분리한다.

### 리스크 3
요금제 비교가 플랜 카드와 중복돼 보일 수 있다.

대응
- 플랜 카드는 선택 유도, 비교표는 의사결정 지원이라는 역할로 분리한다.

## 완료 기준

- 랜딩, 요금제, 체크아웃 세 화면이 실제 동작하는 흐름으로 연결된다.
- checkout에 loading / empty / error / success 상태가 포함된다.
- 관련 테스트가 추가되고 통과한다.
- `npm.cmd run lint`
- `npm.cmd run typecheck`
- `npm.cmd run test`
- `npm.cmd run build`
