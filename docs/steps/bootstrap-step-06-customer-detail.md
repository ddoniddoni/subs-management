# 실행 계획 - Bootstrap Step 06 고객 상세 화면 심화

## 목적

Step 05에서 관리자 액션 워크플로우를 붙였다면, 이번 단계에서는 운영자가 한 명의 고객을 깊게 파악할 수 있는 상세 화면을 만든다. 고객별 구독 상태, 결제 이력, 환불 검토, 쿠폰 보상, 감사 이벤트를 한곳에서 읽을 수 있게 해 운영 콘솔의 현실감을 높인다.

## 이번 단계에서 할 일

- `/admin/customers/[customerId]` 상세 페이지 추가
- 고객 프로필, 구독 요약, 결제 이력, 환불 이력, 쿠폰 이력, 감사 타임라인 구성
- `/admin/customers`, `/admin/payments`, `/admin/refunds`에서 고객 상세 링크 연결
- 상세 화면에 대한 최소 테스트 추가

## 이번 단계에서 하지 않을 일

- 실제 서버 데이터 페칭
- 상세 화면에서 직접 상태 변경 저장
- 관리자 권한별 상세 화면 분기
- 대규모 탭/드로어 시스템 도입
- E2E 테스트 도입

## 우선 대상 화면

### 1. `/admin/customers/[customerId]`
- 고객 프로필 요약
- 현재 구독과 플랜 정보
- 결제 이력
- 환불 이력
- 쿠폰 이력
- 감사 이벤트 타임라인

### 2. `/admin/customers`
- 고객명 또는 액션 영역에서 상세 페이지 진입점 추가

### 3. `/admin/payments`, `/admin/refunds`
- 고객 후속 확인을 위한 상세 링크 추가

## 구현 방향

### 1. 고객 운영 컨텍스트 통합
- 고객 관련 데이터는 `customerId` 기준으로 조합한다.
- 상단은 운영 요약, 하단은 이력성 정보로 나눠 읽기 흐름을 만든다.

### 2. 상세 화면 UX
- 운영자가 “지금 어떤 상태인지”를 빠르게 파악할 수 있도록 상태 배지와 KPI를 먼저 노출한다.
- 결제, 환불, 쿠폰, 감사 이벤트는 각각 독립된 섹션으로 나눠 유지보수하기 쉽게 만든다.

### 3. 오류 및 빈 상태
- 없는 고객 ID는 조용히 실패하지 않고 명확한 에러 상태를 보여준다.
- 섹션별로 데이터가 없을 수 있으므로 빈 상태 문구를 함께 제공한다.

## 구현 원칙

- 실제 제품의 고객 상세 페이지처럼 운영 정보가 한 번에 읽히도록 설계한다.
- 기존 도메인 타입과 상태 메타데이터를 재사용한다.
- 클라이언트 상태 없이 서버 컴포넌트 중심으로 구현 가능한 부분은 서버 컴포넌트로 유지한다.
- 상세 화면은 읽기 중심으로 시작하고, 액션은 기존 화면으로 이어지는 링크 수준에서 멈춘다.

## 리스크

### 리스크 1
상세 화면에 정보가 너무 많아 한 번에 읽기 어려울 수 있다.

대응:
- 상단 요약과 하단 이력 섹션을 분리하고, 우선순위가 높은 정보부터 배치한다.

### 리스크 2
목업 데이터가 적어 상세 페이지가 빈약해 보일 수 있다.

대응:
- 현재 데이터에 맞는 빈 상태 문구와 기본 요약 카드를 넣어 화면 완성도를 유지한다.

### 리스크 3
고객 상세 진입점이 없으면 운영 흐름상 화면이 고립될 수 있다.

대응:
- 고객, 결제, 환불 화면 모두에서 상세 링크를 제공해 운영 맥락을 연결한다.

## 완료 기준

- `/admin/customers/[customerId]`가 동작한다.
- 고객 관련 구독/결제/환불/쿠폰/감사 이력이 한 화면에서 보인다.
- 고객, 결제, 환불 화면에서 상세 페이지로 진입할 수 있다.
- 존재하지 않는 고객은 에러 상태를 보여준다.
- 최소 테스트가 추가되고 통과한다.
- `npm run lint`
- `npm run typecheck`
- `npm run test`
- `npm run build`
