# 실행 계획 - Bootstrap Step 05 관리자 액션 워크플로우 구성

## 목적

Step 04에서 연결한 도메인 데이터와 운영 화면 위에, 실제 관리자 제품다운 핵심 액션 흐름을 추가한다. 이번 단계에서는 단순 조회를 넘어서 상태 변경, 승인/반려, 실패 대응 같은 운영 작업의 기본 UX를 만든다.

## 이번 단계에서 할 일

- 구독 상태 변경 흐름 추가
- 환불 승인 / 반려 흐름 추가
- 결제 실패 대응 흐름 추가
- 고위험 액션에 대한 확인 UI와 결과 피드백 추가
- 액션 전후 상태가 화면에 즉시 반영되도록 로컬 상태 흐름 구성

## 이번 단계에서 하지 않을 일

- 실제 서버 저장
- 실제 인증 / 권한 검사
- 낙관적 업데이트와 롤백 처리
- 대규모 폼 시스템 구축
- E2E 테스트 도입

## 우선 대상 화면

### 1. `/admin/customers`
- 고객별 구독 상태 변경 진입점
- `활성`, `일시 중지`, `해지 예정` 등 상태 전환 흐름

### 2. `/admin/refunds`
- 환불 요청 목록
- 승인 / 반려 액션
- 반려 사유 입력 또는 간단한 코멘트 구조

### 3. `/admin/payments`
- 실패 결제 목록
- 재시도 필요 상태 표시
- 고객 후속 대응을 위한 액션 버튼 또는 상태 업데이트

## 구현 방향

### 1. 상태 변경 UX
- 액션 버튼을 누르면 바로 변경하지 않고 확인 단계를 둔다.
- 변경 후에는 성공 또는 실패 피드백이 보여야 한다.
- 상태 배지와 요약 카드가 변경 결과를 반영해야 한다.

### 2. 환불 처리 UX
- 요청 상태와 처리 완료 상태를 명확히 구분한다.
- 승인 / 반려는 서로 다른 시각적 강조를 사용한다.
- 반려 시 사유가 보존되도록 간단한 로컬 상태를 둔다.

### 3. 결제 실패 대응 UX
- 실패 결제는 별도 섹션이나 눈에 띄는 상태로 보여준다.
- 운영자가 다음 액션을 이해할 수 있도록 버튼 라벨과 설명을 명확히 둔다.
- 실제 외부 결제 재시도 대신 상태 전환형 목업으로 구현한다.

## 구현 원칙

- 액션은 관리자 제품답게 신중한 흐름으로 설계한다.
- 버튼만 늘어놓지 말고, 현재 상태와 결과가 함께 읽히게 만든다.
- 하드코딩 문자열 대신 기존 도메인 타입과 상태 메타데이터를 재사용한다.
- 최소한의 클라이언트 상태만 사용하고, 화면별 상태 범위를 작게 유지한다.

## 리스크

### 리스크 1
로컬 상태 기반 액션 흐름이 실제 제품과 너무 다르게 보일 수 있다.

대응:
- 저장 방식은 목업이더라도 상태 전이와 확인 UX는 현실적으로 설계한다.

### 리스크 2
한 단계에 너무 많은 액션을 넣어 화면이 복잡해질 수 있다.

대응:
- 이번 단계는 고객, 환불, 결제 3개 흐름만 우선 다루고 나머지는 이후로 넘긴다.

### 리스크 3
확인 UI가 없으면 관리자 제품으로서 설득력이 약해질 수 있다.

대응:
- 최소한의 확인 모달 또는 인라인 확인 패턴을 반드시 포함한다.

## 완료 기준

- 고객 구독 상태 변경 흐름이 동작한다.
- 환불 승인 / 반려 흐름이 동작한다.
- 결제 실패 대응 흐름이 동작한다.
- 액션 전후 상태가 화면에 반영된다.
- 사용자 피드백 문구가 한글로 제공된다.
- `npm run lint`
- `npm run typecheck`
- `npm run build`
