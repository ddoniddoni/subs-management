# 실행 계획 - Bootstrap Step 07 감사 로그 화면 심화

## 목적

Step 06에서 고객 상세 화면으로 운영 맥락을 넓혔다면, 이번 단계에서는 이벤트 단위 추적을 위한 감사 로그 화면을 구현한다. 운영자가 누가 어떤 리소스에 어떤 변경을 했는지 빠르게 확인하고, 관련 화면으로 다시 이동할 수 있는 추적 허브를 만든다.

## 이번 단계에서 할 일

- `/admin/audit-log` 실제 화면 구현
- 관리자 필터와 엔티티 유형 필터 추가
- 이벤트 테이블과 최근 타임라인 구성
- 관련 리소스로 이동 가능한 링크 제공
- 감사 로그 화면에 대한 최소 테스트 추가

## 이번 단계에서 하지 않을 일

- 실제 서버 검색
- 날짜 범위 고급 검색
- 무한 스크롤 또는 페이지네이션
- CSV 내보내기
- E2E 테스트 도입

## 우선 대상 화면

### 1. `/admin/audit-log`
- 이벤트 요약 KPI
- 수행자 필터
- 엔티티 유형 필터
- 감사 이벤트 테이블
- 최근 이벤트 타임라인

## 구현 방향

### 1. 추적 가능성 강화
- 이벤트에는 수행자, 엔티티 유형, 액션 요약, 시점이 항상 함께 보이게 한다.
- 가능한 경우 고객 상세나 관련 운영 화면으로 이동 가능한 링크를 붙인다.

### 2. 화면 구조
- 상단은 운영 요약 카드, 중간은 필터, 하단은 테이블과 타임라인으로 구성한다.
- 이벤트량이 적은 현재 단계에서는 페이지네이션보다 가독성과 탐색성을 우선한다.

### 3. 필터 방식
- URL 쿼리 기반 필터를 사용해 서버 컴포넌트 구조를 유지한다.
- 필터가 모두 해제된 기본 상태도 의미 있게 보이도록 만든다.

## 구현 원칙

- 감사 로그는 장식이 아니라 실제 운영 추적을 돕는 화면이어야 한다.
- 도메인 타입과 관리자 역할 메타데이터를 재사용한다.
- 링크 해석 로직은 화면 컴포넌트 밖 helper로 분리한다.
- 데이터가 비어도 빈 상태 문구가 명확해야 한다.

## 리스크

### 리스크 1
목업 감사 이벤트가 적어 화면이 비어 보일 수 있다.

대응:
- 샘플 이벤트를 보강하고, KPI와 타임라인을 함께 보여 완성도를 높인다.

### 리스크 2
이벤트별 링크 규칙이 분산되면 유지보수가 어려워질 수 있다.

대응:
- 엔티티 유형별 링크 생성 규칙을 중앙 helper로 정리한다.

### 리스크 3
필터 UI가 복잡해지면 초기 단계에 비해 과도한 구현이 될 수 있다.

대응:
- 관리자와 엔티티 유형 두 축만 먼저 도입하고, 날짜 필터는 이후 단계로 미룬다.

## 완료 기준

- `/admin/audit-log`가 플레이스홀더가 아닌 실제 화면으로 동작한다.
- 관리자와 엔티티 유형 필터가 동작한다.
- 이벤트별 수행자, 요약, 시점, 링크가 표시된다.
- 이벤트가 없는 조건에서는 빈 상태가 보인다.
- 최소 테스트가 추가되고 통과한다.
- `npm run lint`
- `npm run typecheck`
- `npm run test`
- `npm run build`
