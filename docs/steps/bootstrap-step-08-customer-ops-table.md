# 실행 계획 - Bootstrap Step 08 고객 운영 테이블 강화

## 목적

Step 07에서 감사 로그를 통해 이벤트 추적 기반을 만들었다면, 이번 단계에서는 `/admin/customers`를 실제 운영자가 탐색 가능한 고객 목록 화면으로 끌어올린다. 검색, 필터, 정렬, 페이지네이션을 붙여 고객 목록이 운영 워크플로우의 진짜 진입점 역할을 하게 만든다.

## 이번 단계에서 할 일

- 고객 검색 추가
- 구독 상태 필터 추가
- 플랜 필터 추가
- 정렬 기준 추가
- 페이지네이션 추가
- 고객 목록 관련 최소 테스트 추가

## 이번 단계에서 하지 않을 일

- 서버 기반 검색 API
- 대용량 가상화
- 벌크 액션
- CSV 내보내기
- E2E 테스트 도입

## 우선 대상 화면

### 1. `/admin/customers`
- 검색 입력
- 상태 필터
- 플랜 필터
- 정렬 선택
- 페이지네이션
- 기존 상태 변경 워크플로우와 연결된 고객 목록

## 구현 방향

### 1. 운영 탐색성 강화
- 고객 목록은 단순 나열이 아니라 탐색 가능한 운영 테이블이 되어야 한다.
- 필터와 정렬은 현재 액션 워크플로우를 방해하지 않고 선택 대상을 좁히는 방식으로 동작해야 한다.

### 2. 화면 구조
- 상단에 탐색용 도구 막대를 배치한다.
- 중간에는 필터가 반영된 테이블을 보여준다.
- 하단에는 선택된 고객에 대한 상태 변경 워크플로우를 유지한다.

### 3. 상태 처리
- 필터 결과가 없으면 빈 상태를 보여준다.
- 현재 페이지와 총 페이지 수가 명확히 드러나야 한다.
- 필터가 바뀌면 페이지는 첫 페이지로 되돌린다.

## 구현 원칙

- 고객 목록은 실제 운영 테이블처럼 읽고 조작하기 쉬워야 한다.
- 목록 파생 로직은 helper로 분리해 테스트 가능하게 만든다.
- 기존 상태 변경 흐름을 망가뜨리지 않도록 선택 로직을 함께 조정한다.
- 상태 문자열과 라벨은 기존 메타데이터를 재사용한다.

## 리스크

### 리스크 1
탐색 기능이 많아지면 기존 액션 화면이 복잡해질 수 있다.

대응:
- 탐색 도구와 액션 패널 역할을 분리하고, 시각적으로도 구획을 나눈다.

### 리스크 2
데이터가 적어 페이지네이션이 과해 보일 수 있다.

대응:
- 구조는 도입하되, 현재 데이터 양에 맞는 단순한 페이지 이동 UX로 유지한다.

### 리스크 3
검색/필터/정렬/페이지네이션 조합에서 버그가 생길 수 있다.

대응:
- helper 테스트와 주요 상호작용 테스트를 함께 추가한다.

- 정렬이 동작한다.
- 페이지네이션이 동작한다.
- 기존 구독 상태 변경 워크플로우가 유지된다.

- `npm run lint`
- `npm run typecheck`
- `npm run test`
- `npm run build`
