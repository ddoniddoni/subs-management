# 실행 계획 - Bootstrap Step 09 환불 상세 화면 심화

## 목적

Step 08에서 고객 목록 탐색성을 강화했다면, 이번 단계에서는 환불 요청 한 건을 깊게 읽을 수 있는 상세 화면을 만든다. 운영자가 환불 상태, 고객 맥락, 결제 정보, 검토 메모, 감사 이벤트를 한 번에 파악할 수 있도록 해 환불 처리 흐름의 완성도를 높인다.

## 이번 단계에서 할 일

- `/admin/refunds/[refundId]` 상세 페이지 추가
- 환불 요약, 고객/결제 컨텍스트, 검토 메모, 감사 타임라인 구성
- `/admin/refunds`와 고객 상세의 환불 이력에서 상세 링크 추가
- 환불 상세 관련 최소 테스트 추가

## 이번 단계에서 하지 않을 일

- 상세 화면에서 직접 승인/반려 저장
- 서버 기반 환불 데이터 조회
- 환불 첨부 파일 또는 증빙 업로드
- E2E 테스트 도입

## 우선 대상 화면

### 1. `/admin/refunds/[refundId]`
- 환불 상태 요약
- 고객 정보
- 결제 정보
- 요청 사유
- 검토 메모
- 감사 타임라인

### 2. `/admin/refunds`
- 각 환불 요청에서 상세 페이지 진입점 추가

### 3. `/admin/customers/[customerId]`
- 고객 환불 이력에서 상세 페이지 진입점 추가

## 구현 방향

### 1. 환불 건 중심 설계
- 고객 상세의 하위 섹션이 아니라, 환불 건 자체를 기준으로 화면을 구성한다.
- 상태, 금액, 요청 사유, 검토 메모가 상단에서 바로 읽혀야 한다.

### 2. 운영 맥락 연결
- 고객 상세와 환불 보드로 돌아갈 수 있는 링크를 제공한다.
- 관련 결제 수단과 요청 시점을 함께 보여 운영 판단 문맥을 유지한다.

### 3. 오류 및 빈 상태
- 없는 환불 ID는 명확한 에러 상태를 보여준다.
- 감사 이벤트가 없는 경우에는 빈 상태 문구를 제공한다.

## 구현 원칙

- 상세 화면은 읽기 중심으로 유지한다.
- 기존 도메인 타입과 상태 메타데이터를 재사용한다.
- 데이터 조합 로직은 helper로 분리해 테스트 가능하게 만든다.
- 기존 환불 보드의 액션 UX를 해치지 않고 보완하는 방향으로 연결한다.

## 리스크

### 리스크 1
환불 보드와 상세 화면의 차이가 모호해질 수 있다.

대응:
- 보드는 액션 중심, 상세는 맥락 확인 중심으로 역할을 분리한다.

### 리스크 2
감사 이벤트가 적어 상세 화면이 비어 보일 수 있다.

대응:
- 빈 상태를 명확히 제공하고, 현재 있는 메모와 상태 정보의 가독성을 높인다.

### 리스크 3
고객 상세와 중복이 늘어날 수 있다.

대응:
- 고객 전체 맥락은 고객 상세, 환불 건 단위 정보는 환불 상세에 집중한다.

## 완료 기준

- `/admin/refunds/[refundId]`가 동작한다.
- 환불 상태, 고객, 결제, 메모, 감사 타임라인이 한 화면에서 보인다.
- 환불 목록과 고객 상세에서 환불 상세로 이동할 수 있다.
- 존재하지 않는 환불 ID는 에러 상태를 보여준다.
- 최소 테스트가 추가되고 통과한다.
- `npm run lint`
- `npm run typecheck`
- `npm run test`
- `npm run build`
