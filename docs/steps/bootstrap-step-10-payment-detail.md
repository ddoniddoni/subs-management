# 실행 계획 - Bootstrap Step 10 결제 상세 화면 심화

## 목적

Step 09에서 환불 상세 화면을 만들었다면, 이번 단계에서는 개별 결제 건을 운영 관점에서 추적할 수 있는 결제 상세 화면을 추가한다. 운영자는 결제 상태만 보는 것이 아니라 고객, 구독, 청구, 환불, 감사 로그까지 함께 보고 판단해야 하므로 `/admin/payments/[paymentId]`를 통해 실제 운영 화면에 가까운 흐름을 완성한다.

## 이번 단계에서 할 일

- `/admin/payments/[paymentId]` 상세 페이지 추가
- 결제 요약, 고객/구독 문맥, 인보이스 정보, 연관 환불, 감사 타임라인 구성
- `/admin/payments`와 고객 상세의 결제 이력에서 상세 링크 연결
- 결제 상세 관련 테스트 추가

## 이번 단계에서 하지 않을 일

- 상세 화면에서 직접 결제 상태를 변경하는 액션 추가
- 실제 서버 기반 결제 조회
- 청구서 PDF 다운로드 같은 부가 기능
- E2E 테스트 도입

## 우선 대상 화면

### 1. `/admin/payments/[paymentId]`
- 결제 상태 요약
- 고객 정보
- 구독 및 플랜 문맥
- 인보이스 정보
- 연관 환불 정보
- 감사 타임라인

### 2. `/admin/payments`
- 각 결제 행에서 상세 화면 진입 링크 추가

### 3. `/admin/customers/[customerId]`
- 결제 이력 테이블에서 결제 상세 화면 진입 링크 추가

## 구현 방향

### 1. 읽기 중심 상세 화면
- 결제 액션은 기존 워크벤치에 남기고, 상세 화면은 결제 건을 분석하는 읽기 중심 레이아웃으로 구성한다.

### 2. 관계 데이터 조합
- 결제 단건을 기준으로 고객, 구독, 플랜, 인보이스, 환불, 감사 이벤트를 helper에서 조합해 UI가 단순하게 렌더링되도록 한다.

### 3. 운영 흐름 연결
- 결제 워크벤치에서 처리 중인 건을 바로 상세로 열 수 있게 하고, 고객 상세에서도 특정 결제 건을 깊게 확인할 수 있게 연결한다.

### 4. 예외 상태 명시
- 존재하지 않는 결제 ID, 연관 환불 없음, 감사 이벤트 없음 같은 상황을 숨기지 않고 화면에서 직접 안내한다.

## 리스크

### 리스크 1
결제 목록 화면과 상세 화면의 역할이 겹쳐 보일 수 있다.

대응
- 목록은 우선 처리와 상태 변경, 상세는 문맥 확인과 이력 추적으로 구분한다.

### 리스크 2
연관 환불이나 감사 이벤트가 없는 결제는 화면 밀도가 떨어질 수 있다.

대응
- 빈 상태 카피를 명확히 두고, 존재하는 정보는 요약 카드와 문맥 블록으로 충분히 보강한다.

### 리스크 3
고객 상세와 정보가 일부 겹칠 수 있다.

대응
- 결제 단건 기준 정보만 집중해서 보여주고, 고객 전체 이력은 고객 상세로 다시 이동할 수 있게 유지한다.

## 완료 기준

- `/admin/payments/[paymentId]`가 동작한다.
- 결제 상태, 고객, 구독, 인보이스, 환불, 감사 이벤트가 한 화면에서 보인다.
- 결제 목록과 고객 상세에서 결제 상세로 이동할 수 있다.
- 존재하지 않는 `paymentId`는 에러 상태로 처리된다.
- 최소 테스트가 추가되고 통과한다.
- `npm.cmd run lint`
- `npm.cmd run typecheck`
- `npm.cmd run test`
- `npm.cmd run build`
