# 실행 계획 - Bootstrap Step 03 공통 UI 프리미티브 구성

## 목적

Step 02에서 만든 고객용 / 관리자용 레이아웃 위에, 이후 화면 구현에 반복적으로 사용할 수 있는 공통 UI 프리미티브를 추가한다.

## 이번 단계에서 할 일

- `PageHeader`를 현재 구조에 맞게 정리하거나 확장
- `StatusBadge` 추가
- `StatCard` 추가
- `EmptyState` 추가
- `ErrorState` 추가
- `LoadingSkeleton` 추가
- `TableShell` 추가
- 최소 1개 이상의 고객용 / 관리자용 페이지에서 새 프리미티브를 실제로 사용

## 이번 단계에서 하지 않을 일

- 실제 도메인 데이터 연결
- 고급 테이블 기능 구현
- 차트 구현
- 모달, 드로어, 드롭다운 같은 인터랙티브 오버레이 구현
- 테스트 환경 확장

## 대상 컴포넌트

### 기본 정보 표시
- `PageHeader`
- `StatusBadge`
- `StatCard`

### 상태 표시
- `EmptyState`
- `ErrorState`
- `LoadingSkeleton`

### 데이터 컨테이너
- `TableShell`

## 구현 방향

### 1. 컴포넌트 위치
- `src/components/ui/` 아래에 공통 UI 프리미티브를 둔다.
- 페이지 전용 조합이 아니라 재사용 가능한 props 중심 인터페이스로 설계한다.

### 2. 디자인 방향
- 현재 고객용 / 관리자용 레이아웃과 어울리는 중립적인 스타일을 유지한다.
- 과한 장식보다 운영 화면에서 반복 사용하기 쉬운 구조를 우선한다.
- 텍스트는 계속 한글 기준으로 유지한다.

### 3. 적용 방식
- 관리자 홈 또는 고객 계정 페이지 같은 기존 플레이스홀더 화면 중 일부에 새 컴포넌트를 적용해본다.
- 아직 실제 도메인 데이터가 없으므로, 샘플 텍스트와 더미 수치 수준에서만 사용한다.

## 구현 원칙

- props 이름은 구체적이되 과하게 많지 않게 유지한다.
- 상태 표현은 이후 도메인 enum과 연결하기 쉬운 형태로 만든다.
- 페이지마다 다른 스타일을 복붙하지 않도록 공통 스타일 책임을 컴포넌트에 둔다.
- Step 04의 도메인 타입 / 목업 데이터 작업과 자연스럽게 연결되도록 설계한다.

## 리스크

### 리스크 1
너무 이른 추상화로 인해 실제 화면 요구와 어긋날 수 있다.

대응:
- 지금 필요한 최소 API만 제공하고, 추상화는 얇게 시작한다.

### 리스크 2
프리미티브가 관리자 화면에만 맞춰질 수 있다.

대응:
- 고객용 화면에서도 쓸 수 있는 범용성을 기준으로 디자인한다.

### 리스크 3
TableShell이 너무 복잡해질 수 있다.

대응:
- 초기에는 헤더, 설명, 컨테이너 역할에 집중하고 정렬/필터/페이지네이션은 후속 단계로 넘긴다.

## 완료 기준

- `src/components/ui/`에 Step 03 대상 컴포넌트가 추가된다.
- 최소 1개 이상의 고객용 화면과 1개 이상의 관리자용 화면에서 새 프리미티브가 사용된다.
- 기존 레이아웃과 시각적으로 충돌하지 않는다.
- `npm run lint`
- `npm run typecheck`
- `npm run build`
