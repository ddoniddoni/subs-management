# 실행 계획 - Bootstrap Step 18 구독 운영 워크벤치 강화

## 목표

step 17에서 `/admin/subscriptions` 전용 화면을 만들었다면, 이번 단계에서는 그 화면을 실제 운영 화면에 더 가깝게 다듬는다. 운영자가 상태만 바꾸는 것이 아니라 왜 바꾸는지 기록하고, 주변 결제 맥락을 함께 보면서 더 안전하게 판단할 수 있게 만드는 것이 핵심이다.

## 이번 단계에서 할 일

- 상태 변경 사유 입력 추가
- 위험 액션별 확인 패널 강화
- 실패 피드백과 성공 피드백 분리
- 최근 결제 / 환불 / 쿠폰 컨텍스트 패널 추가
- 구독 운영 helper 및 테스트 갱신

## 이번 단계에서 하지 않을 일

- 실제 서버 저장
- 서버 액션 도입
- 벌크 상태 변경
- 실시간 polling
- 새 관리자 라우트 추가

## 대상 화면

### 1. `/admin/subscriptions`
- 구독 검색 / 필터 / 정렬 / 페이지네이션
- 선택된 구독 컨텍스트
- 상태 전환 이유 입력
- 확인 절차
- 최근 운영 activity feed

## 구현 방향

### 1. soft guardrail 우선
- 상태 전환 자체를 과도하게 막기보다, 사유 입력과 명확한 경고 문구로 안전성을 높인다.
- 성공과 실패 피드백을 분리해 운영자가 지금 무엇이 막혔는지 바로 이해할 수 있게 한다.

### 2. 판단 맥락을 한 화면에 모으기
- 최근 결제 상태, 환불 요청 여부, 적용 쿠폰을 함께 보여준다.
- 운영자가 고객 상세나 결제 화면으로 계속 왕복하지 않아도 기본 판단이 가능하도록 만든다.

### 3. 상호작용 성능 정리
- 검색/필터/선택 업데이트는 기존 패턴을 유지하되 비긴급 업데이트는 `startTransition`으로 감싼다.
- 파생 상태는 effect보다 render 계산을 우선한다.

## 리스크

### 리스크 1
입력 필드와 컨텍스트 카드가 늘면서 화면이 복잡해질 수 있다.

대응:
- 상태 변경 액션 영역과 운영 컨텍스트 영역을 분리해 스캔 가능성을 유지한다.

### 리스크 2
사유 입력 validation이 테스트와 충돌할 수 있다.

대응:
- 기존 테스트를 갱신하고 validation 성공/실패를 모두 명시적으로 검증한다.

### 리스크 3
목업 데이터 기준으로 일부 구독은 환불이나 쿠폰 정보가 비어 있을 수 있다.

대응:
- 각 컨텍스트 섹션마다 빈 상태 문구를 제공한다.

## 완료 기준

- `/admin/subscriptions`에서 사유 없는 상태 변경 시도가 실패 피드백으로 막힌다.
- 사유를 입력하고 상태 변경하면 성공 피드백과 activity feed가 갱신된다.
- 선택한 구독의 결제 / 환불 / 쿠폰 컨텍스트가 보인다.
- 관련 테스트가 통과한다.
- `npm.cmd run lint`
- `npm.cmd run typecheck`
- `npm.cmd run test`
- `npm.cmd run build`
