# Step 07 감사 로그 화면 실행 계획

## 목표

- `/admin/audit-log`를 실제 운영 콘솔처럼 추적 가능한 감사 로그 화면으로 구현한다.
- 누가, 어떤 리소스에, 어떤 액션을 수행했는지 필터와 링크를 통해 빠르게 확인할 수 있게 만든다.
- 기존 목업 이벤트를 단순 나열하지 않고, 관리자/엔티티/시점 기준으로 읽기 쉬운 구조로 정리한다.

## 가정

- 실제 서버 저장이나 대규모 검색 인덱스 없이 목업 `auditEvents`와 관련 도메인 데이터를 조합해 구현한다.
- 초기 버전은 서버 컴포넌트 기반의 URL 쿼리 필터로 충분하다.
- 이벤트 수가 적으므로 페이지네이션보다는 필터와 타임라인 가독성을 우선한다.

## 범위

- `/admin/audit-log` 페이지 구현
- 관리자, 엔티티 유형 기준 필터 추가
- 테이블과 타임라인 형태의 감사 이벤트 요약 추가
- 관련 리소스로 이동 가능한 링크 연결
- 감사 로그 페이지를 위한 최소 테스트 추가

## 구현 단계

1. 감사 로그 표시용 파생 데이터 구성
   - `auditEvents`, `adminUsers`, 관련 도메인 리소스를 묶어 표시용 라벨과 링크를 만든다.
2. 페이지 구현
   - KPI 카드
   - URL 쿼리 기반 필터
   - 감사 이벤트 테이블
   - 최근 이벤트 타임라인
   - 빈 상태와 에러 없는 초기 상태 구성
3. 링크 연결
   - 가능한 이벤트는 고객 상세나 기존 운영 화면으로 이동 가능한 링크를 제공한다.
4. 테스트와 검증
   - 필터링 로직과 렌더링 핵심을 검증한다.
   - `npm run lint`
   - `npm run typecheck`
   - `npm run test`
   - `npm run build`

## 리스크

- 목업 이벤트가 적으면 감사 로그 화면이 빈약해 보일 수 있다.
  - 대응: 이벤트 샘플을 보강하고 KPI/필터/타임라인을 함께 제공한다.
- 이벤트별 링크 규칙이 제각각이면 유지보수가 어려워질 수 있다.
  - 대응: 엔티티 타입별 링크 해석 로직을 helper로 모은다.
- 클라이언트 필터를 과하게 쓰면 단순 화면에 비해 복잡도가 커질 수 있다.
  - 대응: 이번 단계는 서버 컴포넌트 + 쿼리 파라미터 기반으로 유지한다.

## 검증 방법

- 관리자와 엔티티 필터가 올바르게 동작하는지 확인한다.
- 각 이벤트의 수행자, 요약, 시점, 관련 리소스 링크가 정상 표시되는지 확인한다.
- 감사 이벤트가 없는 조건에서는 빈 상태가 보이는지 확인한다.
