# Step 15 고객 계정 센터 실행 계획

## 목표

- `/app/subscription`과 `/app/billing`을 단순 조회 화면에서 실제 self-service account center 수준으로 끌어올린다.
- 고객이 현재 구독 상태, 다음 청구, 할인 적용, 최근 결제 이상 징후를 한눈에 이해할 수 있게 한다.
- 청구 이력과 결제 상태를 재사용 가능한 snapshot/helper 구조로 정리해 이후 고객 기능 확장 기반을 만든다.

## 가정

- 실제 계정 인증 없이 `currentCustomerId` 기반 목업 고객 세션을 유지한다.
- 고객이 수행하는 액션은 실제 변경이 아니라 안내/추천 액션 수준으로 표현한다.
- 결제 내역 필터링과 정렬은 클라이언트 UI에서 수행하고, 계산 로직은 helper로 분리한다.

## 범위

- 고객 계정 snapshot/helper 추가
- `/app/subscription` 페이지 고도화
- `/app/billing` 페이지 고도화
- 관련 테스트 추가

## 구현 단계

1. 고객 계정 helper 설계
   - 구독 상태 요약
   - 결제 건강도
   - 최근 청구/환불/쿠폰 이력
   - self-service 추천 액션
2. 내 구독 화면 구현
   - 헤드라인 카드
   - 상태 요약 배지
   - 구독 타임라인
   - 권장 다음 액션
   - 쿠폰 / 최근 결제 상태 연결
3. 결제 내역 화면 구현
   - 결제 상태 요약 카드
   - 상태 필터 / 정렬
   - 청구 이력 테이블
   - 결제 실패/환불 안내 패널
4. 테스트 및 검증
   - helper 테스트
   - billing 인터랙션 테스트
   - `npm.cmd run lint`
   - `npm.cmd run typecheck`
   - `npm.cmd run test`
   - `npm.cmd run build`

## 리스크

- 고객용 페이지가 운영자용 상세와 중복돼 보일 수 있다.
  - 고객 시점에서는 "내가 지금 무엇을 해야 하는가" 중심으로 단순화한다.
- 결제 이력이 적어 필터 UI 가치가 약할 수 있다.
  - 요약 카드와 상태 설명을 함께 두어 의미를 보강한다.
- account center가 액션 가능한 화면처럼 과도하게 보일 수 있다.
  - 실제 변경이 아닌 안내/진입 CTA 중심으로 설계한다.

## 검증 방법

- 현재 고객의 구독 상태, 다음 청구일, 할인 혜택, 최근 결제 이상 징후가 helper 결과와 일치하는지 확인한다.
- billing 화면에서 상태 필터와 정렬이 정상 동작하는지 확인한다.
- 빈 데이터나 잘못된 고객 세션에서도 안전한 empty/error 상태가 노출되는지 확인한다.
- 전체 검증 명령 `lint`, `typecheck`, `test`, `build`가 모두 통과하는지 확인한다.
