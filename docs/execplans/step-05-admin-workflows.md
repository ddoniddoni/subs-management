# Step 05 관리자 액션 워크플로우 실행 계획

## 목표

- 관리자 콘솔의 핵심 액션 흐름을 실제 운영 제품처럼 보이도록 강화한다.
- 고객 구독 상태 변경, 환불 승인/반려, 실패 결제 대응을 확인 절차와 결과 피드백까지 포함해 완성한다.
- 반복되는 확인/피드백 패턴은 재사용 가능한 UI로 정리하고, 최소 테스트 기반을 추가한다.

## 가정

- 실제 서버 저장, 인증, 권한 검사는 아직 범위 밖이며 로컬 상태 기반 목업으로 진행한다.
- 기존 `src/mocks/subscription-data.ts`의 도메인 데이터와 `auditEvents`를 초기 운영 이력의 근거로 사용한다.
- 테스트 러너가 아직 없으므로 이번 단계에서 `npm run test`를 지원하도록 최소 구성을 추가한다.

## 범위

- `/admin/customers`의 구독 상태 변경 워크플로우 보강
- `/admin/refunds`의 환불 승인/반려 워크플로우 보강
- `/admin/payments`의 결제 실패 대응 워크플로우 보강
- 공통 액션 피드백 배너와 최근 처리 이력 UI 추가
- 핵심 워크플로우 3종에 대한 테스트 추가

## 구현 단계

1. 공통 액션 UI 정의
   - 성공 피드백 배너와 최근 처리 이력 컴포넌트를 추가한다.
   - 날짜/시간 표시 유틸리티를 보강한다.
2. 워크플로우 반영
   - 세 관리자 화면에서 공통 UI를 재사용하도록 정리한다.
   - 액션 완료 시 로컬 상태와 최근 처리 이력이 즉시 반영되도록 연결한다.
3. 테스트 기반 추가
   - Vitest + Testing Library 기반 테스트 환경을 구성한다.
   - 구독 상태 변경, 환불 승인/반려, 결제 실패 대응 흐름을 검증한다.
4. 검증 및 문서 정리
   - `npm run lint`
   - `npm run typecheck`
   - `npm run test`
   - `npm run build`

## 리스크

- 공통화가 과하면 각 워크플로우의 차이를 가릴 수 있다.
  - 대응: 시각 구조만 재사용하고, 각 도메인의 문구와 상태 로직은 컴포넌트별로 유지한다.
- 테스트 도입 시 경로 별칭이나 DOM 환경 설정으로 초기 오류가 날 수 있다.
  - 대응: 최소 설정만 추가하고, 현재 Next.js 구조와 충돌하지 않는 방향으로 구성한다.
- 로컬 상태 기반 이력이 실제 감사 로그처럼 과장되어 보일 수 있다.
  - 대응: 목업 이력임을 유지하되, 도메인 이벤트 요약과 처리 시점을 중심으로 현실적인 문구를 사용한다.

## 검증 방법

- 액션 전후 상단 KPI 수치와 상태 배지가 즉시 바뀌는지 확인한다.
- 확인 단계를 거치지 않으면 상태가 바뀌지 않는지 확인한다.
- 액션 완료 후 피드백 배너와 최근 처리 이력에 변경 내용이 반영되는지 확인한다.
- 세 워크플로우의 핵심 동작이 테스트에서 통과하는지 확인한다.
