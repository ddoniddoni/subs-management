# Step 09 환불 상세 화면 실행 계획

## 목표

- `/admin/refunds/[refundId]` 라우트를 구현해 환불 요청 한 건을 깊게 검토할 수 있는 상세 화면을 만든다.
- 고객, 결제, 검토 메모, 처리 이력, 관련 감사 이벤트를 한 화면에서 연결해 운영 판단을 쉽게 한다.
- 환불 목록과 고객 상세 화면에서 환불 상세로 자연스럽게 이동할 수 있게 한다.

## 가정

- 실제 서버 API 없이 기존 목업 데이터만으로 상세 화면을 조합한다.
- 환불 상세는 읽기 중심으로 시작하고, 승인/반려 같은 액션은 기존 `/admin/refunds` 워크플로우에서 수행하도록 유지한다.
- 존재하지 않는 `refundId`에 대해서는 명확한 에러 상태를 보여준다.

## 범위

- `/admin/refunds/[refundId]` 페이지 구현
- 환불 요약, 고객 컨텍스트, 결제 정보, 검토 메모, 감사 타임라인 구성
- `/admin/refunds`, `/admin/customers/[customerId]`에서 환불 상세 링크 추가
- 관련 helper와 테스트 추가

## 구현 단계

1. 환불 상세 파생 데이터 helper 추가
   - 환불, 고객, 결제, 구독, 감사 이벤트를 묶는다.
2. 상세 페이지 구현
   - 환불 상태와 금액 요약
   - 고객/결제 컨텍스트
   - 검토 메모와 처리 결과
   - 관련 감사 타임라인
   - 에러 및 빈 상태
3. 진입 링크 연결
   - 환불 검토 보드
   - 고객 상세의 환불 이력 테이블
4. 테스트와 검증
   - helper 테스트
   - 주요 렌더링 테스트
   - `npm run lint`
   - `npm run typecheck`
   - `npm run test`
   - `npm run build`

## 리스크

- 환불 액션 화면과 상세 화면의 역할이 겹쳐 보일 수 있다.
  - 대응: 상세는 읽기 중심, 액션은 목록 보드 중심으로 역할을 분리한다.
- 목업 감사 이벤트가 적어 타임라인이 빈약할 수 있다.
  - 대응: 현재 데이터 기준으로 빈 상태를 허용하되, 관련 이벤트가 있는 건에서는 링크와 수행자 정보를 분명히 보여준다.
- 환불 상세가 고객 상세와 중복되어 보일 수 있다.
  - 대응: 환불 건 자체의 검토 정보와 처리 문맥에 집중한다.

## 검증 방법

- 환불 상세에서 고객, 결제, 메모, 상태가 올바르게 묶여 보이는지 확인한다.
- 존재하지 않는 `refundId`에서 에러 상태가 보이는지 확인한다.
- 환불 목록과 고객 상세에서 환불 상세로 이동 가능한지 확인한다.
