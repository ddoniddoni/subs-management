# Step 08 고객 운영 테이블 실행 계획

## 목표

- `/admin/customers`를 운영자가 실제로 탐색 가능한 고객 목록 화면으로 강화한다.
- 검색, 상태 필터, 플랜 필터, 정렬, 페이지네이션을 추가해 고객 규모가 커져도 탐색 가능한 구조를 만든다.
- 기존 구독 상태 변경 워크플로우와 목록 탐색 흐름이 한 화면 안에서 자연스럽게 이어지게 정리한다.

## 가정

- 실제 서버 API 없이 기존 목업 데이터를 클라이언트 상태에서 조합해 구현한다.
- 현재 데이터 양은 작지만, UI 구조는 더 큰 목록에도 확장 가능한 방향으로 설계한다.
- 기존 상태 변경 워크플로우는 유지하되, 목록 탐색과 선택 경험을 먼저 개선한다.

## 범위

- `/admin/customers` 검색 입력
- 구독 상태 필터
- 플랜 필터
- 고객명/최근 결제/다음 청구일 기준 정렬
- 페이지네이션
- 관련 테스트 추가

## 구현 단계

1. 목록 데이터 파생 로직 분리
   - 고객/구독/플랜/결제 데이터를 테이블 행 모델로 정리한다.
   - 검색, 필터, 정렬, 페이지네이션 helper를 분리한다.
2. 화면 구현
   - 필터 바와 정렬 선택 UI 추가
   - 페이지네이션 상태 추가
   - 선택된 고객 워크플로우와 테이블 탐색이 충돌하지 않도록 조정
3. 테스트 추가
   - 고객 검색
   - 상태 필터
   - 정렬 및 페이지 전환
4. 검증
   - `npm run lint`
   - `npm run typecheck`
   - `npm run test`
   - `npm run build`

## 리스크

- 목록 UI와 상태 변경 워크플로우가 한 페이지에 함께 있어 복잡해질 수 있다.
  - 대응: 상단은 탐색, 하단은 선택된 고객 액션이라는 역할 분리를 분명히 한다.
- 작은 데이터셋에서는 페이지네이션 가치가 약해 보일 수 있다.
  - 대응: 페이지네이션 구조는 유지하되, 현재 데이터에 맞는 직관적 문구를 제공한다.
- 클라이언트 상태가 많아지면 테스트가 흔들릴 수 있다.
  - 대응: 파생 로직을 helper로 분리하고 테스트는 helper와 주요 상호작용 둘 다 검증한다.

## 검증 방법

- 검색어 입력 시 일치 고객만 남는지 확인한다.
- 상태/플랜 필터 조합이 올바르게 반영되는지 확인한다.
- 정렬 기준 변경 시 행 순서가 바뀌는지 확인한다.
- 페이지 이동 시 현재 페이지의 고객만 표시되는지 확인한다.
