# Step 14 고객 획득 흐름 실행 계획

## 목표

- 고객용 앱의 첫 진입 흐름인 `/`, `/pricing`, `/checkout`을 실제 제품처럼 보이는 화면으로 전환한다.
- 운영 콘솔 중심 제품이라는 정체성을 유지하면서도 고객이 상품을 이해하고 결제까지 이어지는 흐름을 자연스럽게 경험할 수 있게 만든다.
- 플랜 비교, 주문 요약, 목업 결제 완료 상태까지 하나의 재사용 가능한 고객 획득 모듈로 정리한다.

## 가정

- 실제 결제 게이트웨이 연동 없이 로컬 상태와 목업 데이터만으로 checkout 성공 흐름을 구현한다.
- `plans` 목업 데이터를 재사용하고, 연간 결제 가격은 월간 가격 기반 할인 계산으로 파생한다.
- checkout은 고객 획득 데모용이므로 폼 제출 후 성공 상태와 오류 상태를 UI에서 시뮬레이션한다.

## 범위

- 랜딩 페이지 구현
- 요금제 비교 페이지 구현
- checkout mock flow 구현
- 고객 획득 helper / snapshot 조합 로직 추가
- 관련 테스트 추가

## 구현 단계

1. 고객 획득 helper 설계
   - 랜딩 hero, 신뢰 지표, FAQ, 플랜 비교, checkout 요약에 필요한 파생 데이터를 정리한다.
2. 랜딩 페이지 구현
   - hero, value proposition, 운영 시나리오, 추천 플랜 미리보기, FAQ, CTA 구성
3. 요금제 페이지 구현
   - billing interval 전환
   - 플랜 카드
   - 기능 비교표
   - checkout 진입 CTA
4. checkout 페이지 구현
   - 선택 플랜 요약
   - 고객 정보 입력
   - 좌석 수 / 결제 주기 변경
   - 쿠폰 / 예상 청구액 / 주문 요약
   - loading / success / error / empty 상태
5. 테스트 및 검증
   - pricing / checkout helper 테스트
   - 주요 고객 흐름 렌더링 테스트
   - `npm.cmd run lint`
   - `npm.cmd run typecheck`
   - `npm.cmd run test`
   - `npm.cmd run build`

## 리스크

- 고객용 화면이 관리자 콘솔과 톤이 너무 분리될 수 있다.
  - 같은 제품 세계관을 유지하되 고객용은 더 따뜻한 카피와 전환 중심 구조로 차별화한다.
- checkout 상호작용이 클라이언트 상태에 과하게 몰릴 수 있다.
  - 계산 로직은 helper에 두고 UI는 상태 전환과 입력만 담당하게 분리한다.
- 기능 비교표가 장식처럼 보일 수 있다.
  - 실제 운영 가치와 연결된 기능 묶음으로 비교 항목을 설계한다.

## 검증 방법

- 랜딩에서 pricing / checkout으로 이어지는 CTA가 정상 연결되는지 확인한다.
- 요금제 billing interval 전환 시 가격과 설명이 올바르게 바뀌는지 확인한다.
- checkout에서 플랜 선택, 좌석 수, 쿠폰, 제출 결과가 의도대로 반영되는지 확인한다.
- 전체 검증 명령 `lint`, `typecheck`, `test`, `build`가 모두 통과하는지 확인한다.
