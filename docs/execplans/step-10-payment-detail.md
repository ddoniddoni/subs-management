# Step 10 결제 상세 화면 실행 계획

## 목표

- `/admin/payments/[paymentId]` 라우트를 추가해 개별 결제 건의 운영 맥락을 한 화면에서 확인할 수 있게 한다.
- 결제 상태, 고객/구독/청구 문맥, 연관 환불, 감사 이벤트를 함께 보여줘 운영자가 다음 액션을 빠르게 판단할 수 있게 한다.
- `/admin/payments`와 고객 상세 화면에서 결제 상세 화면으로 자연스럽게 이동할 수 있게 연결한다.

## 가정

- 실제 서버 API 없이 기존 목업 데이터만으로 결제 상세 화면을 조합한다.
- 결제 상태 변경 액션은 계속 `/admin/payments` 워크벤치에서 수행하고, 상세 화면은 읽기 중심으로 유지한다.
- 존재하지 않는 `paymentId`는 명확한 에러 상태로 처리한다.

## 범위

- `/admin/payments/[paymentId]` 페이지 구현
- 결제 상세 스냅샷 helper 추가
- 결제 상태 요약, 고객/구독 문맥, 연관 환불, 감사 타임라인 UI 구성
- `/admin/payments`, `/admin/customers/[customerId]`에서 결제 상세 링크 연결
- 관련 테스트 추가

## 구현 단계

1. 결제 상세 스냅샷 helper 작성
   - 결제, 고객, 구독, 플랜, 인보이스, 환불, 감사 이벤트를 한 번에 조합한다.
2. 상세 페이지와 뷰 구현
   - 상태 요약 카드
   - 고객 및 구독 문맥
   - 청구 정보와 결제 시도 정보
   - 연관 환불 정보
   - 감사 이벤트 타임라인
   - 빈 상태 및 에러 상태
3. 진입 링크 연결
   - 결제 실패 대응 화면
   - 고객 상세의 결제 이력 테이블
4. 테스트 및 검증
   - helper 테스트
   - 주요 렌더링/링크 테스트
   - `npm.cmd run lint`
   - `npm.cmd run typecheck`
   - `npm.cmd run test`
   - `npm.cmd run build`

## 리스크

- 결제 상세가 기존 워크벤치와 역할이 겹쳐 보일 수 있다.
  - 대응: 워크벤치는 액션 중심, 상세 화면은 문맥 확인 중심으로 분리한다.
- 목업 데이터 기준으로는 연관 감사 이벤트가 적어 화면이 비어 보일 수 있다.
  - 대응: 빈 상태를 명확히 제공하고, 필요한 최소 이벤트만 연결한다.
- 결제, 인보이스, 환불 관계가 일부 데이터에서 비어 있을 수 있다.
  - 대응: null-safe helper를 만들고 화면에서 누락 상태를 직접 표현한다.

## 검증 방법

- 결제 상세에서 고객, 구독, 청구, 환불, 감사 이벤트가 올바르게 묶여 보이는지 확인한다.
- 존재하지 않는 `paymentId`에서 에러 상태가 보이는지 확인한다.
- 결제 목록과 고객 상세에서 결제 상세로 이동 가능한지 확인한다.
