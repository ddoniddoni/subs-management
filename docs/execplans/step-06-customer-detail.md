# Step 06 고객 상세 화면 실행 계획

## 목표

- `/admin/customers/[customerId]` 라우트를 구현해 한 명의 고객에 대한 운영 정보를 한곳에서 파악할 수 있게 만든다.
- 고객 목록, 결제 대응, 환불 검토 화면에서 고객 상세로 자연스럽게 이동할 수 있도록 연결한다.
- 고객 상세 화면은 실제 운영 콘솔처럼 프로필, 구독 요약, 결제 이력, 환불 이력, 쿠폰 이력, 감사 타임라인을 함께 보여준다.

## 가정

- 실제 서버 조회 대신 기존 목업 데이터에서 고객 관련 리소스를 조합해 화면을 구성한다.
- 상세 화면은 읽기 중심으로 시작하고, 고위험 액션은 후속 단계에서 연결 가능한 진입점 수준으로 유지한다.
- 존재하지 않는 `customerId`에 대해서는 빈 상태가 아니라 명확한 오류 상태를 보여준다.

## 범위

- `/admin/customers/[customerId]` 페이지 구현
- 고객 프로필, 구독 상태, 최근 결제/환불/쿠폰/감사 이벤트 섹션 구성
- `/admin/customers`, `/admin/payments`, `/admin/refunds`에서 고객 상세 링크 추가
- 고객 상세 페이지에 대한 최소 테스트 추가

## 구현 단계

1. 상세 화면 데이터 조합
   - 고객, 구독, 결제, 환불, 쿠폰, 감사 이벤트를 `customerId` 기준으로 묶는다.
   - 요약 카드와 타임라인용 파생 데이터를 만든다.
2. 페이지 구현
   - 고객 프로필 헤더와 운영 요약 카드 배치
   - 구독 요약, 결제 이력, 환불 이력, 쿠폰 이력, 감사 타임라인 섹션 구현
   - 존재하지 않는 고객에 대한 오류 상태 추가
3. 진입점 연결
   - 고객 목록, 결제, 환불 화면에서 고객 상세 링크 연결
4. 테스트와 검증
   - 고객 상세 페이지 렌더링과 링크 진입을 최소 범위로 검증
   - `npm run lint`
   - `npm run typecheck`
   - `npm run test`
   - `npm run build`

## 리스크

- 고객 상세 화면에 너무 많은 정보를 한 번에 넣으면 읽기 어려워질 수 있다.
  - 대응: 상단 요약과 하단 이력 섹션으로 분리하고, 우선순위가 높은 정보부터 배치한다.
- 목업 데이터 양이 작아 상세 화면이 비어 보일 수 있다.
  - 대응: 현재 데이터에 맞는 빈 상태 문구를 각 섹션에 제공한다.
- 여러 화면에 링크를 추가하면서 문구와 레이아웃이 흔들릴 수 있다.
  - 대응: 기존 버튼 스타일을 유지하고, 링크는 운영 흐름에 필요한 위치에만 추가한다.

## 검증 방법

- 고객 상세 진입 시 관련 구독/결제/환불/쿠폰/감사 이벤트가 올바르게 묶여 보이는지 확인한다.
- 존재하지 않는 고객 ID에 대해 오류 상태가 노출되는지 확인한다.
- 고객 목록, 결제, 환불 화면에서 상세 링크가 정상 라우트로 연결되는지 확인한다.
