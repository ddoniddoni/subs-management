# Step 13 관리자 권한 / 접근 제어 실행 계획

## 목표

- `/admin/admin-users`를 실제 운영자 권한 관리 화면으로 전환한다.
- 역할별 접근 가능 화면과 운영 권한을 한눈에 볼 수 있는 요약 구조를 만든다.
- 관리자 레이아웃에 최소한의 권한 가드를 추가해, 선택된 운영자 역할에 따라 접근 가능한 화면만 노출되도록 한다.

## 가정

- 백엔드 인증 연동 없이 목업 운영자 데이터와 역할 정책만으로 v1 접근 제어를 구현한다.
- 실제 보안 경계가 아니라 프론트엔드 운영 콘솔의 역할 기반 가시성 및 가드 흐름을 보여주는 단계다.
- 운영자 세션은 상단 전환 UI와 쿼리 파라미터를 사용해 모의 전환한다.

## 범위

- 관리자 역할별 라우트 권한 정책 정의
- 운영자 권한/역할 요약 helper 추가
- `/admin/admin-users` 실화면 구현
- 관리자 레이아웃 권한 가드 및 네비게이션 필터링 추가
- 권한 helper 및 가드 동작 테스트 추가

## 구현 단계

1. 역할 정책 정의
   - 관리자 역할별 설명, 핵심 권한, 라우트 허용 범위를 상수로 정리한다.
   - 현재 경로가 허용 대상인지 판별하는 helper를 만든다.
2. 관리자 권한 화면 구성 데이터 준비
   - 운영자 목록, 최근 감사 로그, 라우트 정책을 조합한 dashboard snapshot을 만든다.
   - 검색 / 역할 필터 / 정렬 / 페이지네이션에 사용할 테이블 helper를 분리한다.
3. `/admin/admin-users` 구현
   - 운영자 현황 카드
   - 역할별 권한 요약 카드
   - 운영자 디렉터리 테이블
   - 라우트 접근 매트릭스
   - 빈 상태 / 오류 상태 포함
4. 관리자 레이아웃 권한 가드 추가
   - 선택된 운영자 역할에 따라 좌측 네비게이션을 필터링한다.
   - 현재 경로가 허용되지 않으면 차단 메시지와 이동 가능한 화면 목록을 보여준다.
5. 테스트 및 검증
   - 권한 helper 테스트
   - 관리자 레이아웃 가드 렌더링 테스트
   - `npm.cmd run lint`
   - `npm.cmd run typecheck`
   - `npm.cmd run test`
   - `npm.cmd run build`

## 리스크

- 프론트엔드 가드는 실제 보안 경계가 아니어서 서버 보호처럼 보일 수 있다.
  - 문서와 UI에서 모의 운영자 세션 기반임을 명확히 드러낸다.
- 라우트 정책이 화면 코드 여기저기에 흩어질 수 있다.
  - 중앙 helper에 정책을 모으고 화면은 helper 결과만 소비한다.
- 운영자 수가 적어 테이블 인터랙션 가치가 약할 수 있다.
  - 필터, 정렬, 페이지네이션을 붙여 이후 실제 데이터 확장에 바로 재사용 가능하게 만든다.

## 검증 방법

- 역할별 허용 라우트 수와 차단 라우트가 의도대로 계산되는지 확인한다.
- `ops_admin`이 아닌 역할로 `/admin/admin-users` 접근 시 차단 메시지가 보이는지 확인한다.
- 관리자 화면에서 검색 / 필터 / 정렬 / 페이지네이션이 정상 동작하는지 확인한다.
- 전체 검증 명령 `lint`, `typecheck`, `test`, `build`가 모두 통과하는지 확인한다.
