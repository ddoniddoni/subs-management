# Step 18 구독 운영 워크벤치 강화 실행 계획

## 목표

- `/admin/subscriptions`를 단순 상태 전환 화면에서 실제 운영 의사결정을 돕는 안전한 워크벤치로 강화한다.
- 위험도가 높은 상태 변경에 사유 입력, 차등화된 확인 문구, 명시적인 실패 피드백을 추가한다.
- 선택한 구독의 최근 결제, 환불, 쿠폰 맥락을 함께 보여줘 운영자가 다른 화면으로 이동하지 않고도 판단할 수 있게 만든다.

## 가정

- 실제 API 연동 없이 기존 목업 데이터와 클라이언트 상태를 기반으로 v1 운영 흐름을 표현한다.
- 상태 전환 자체는 로컬 목업 업데이트로 유지하되, 사유와 감사성 메모는 activity feed에 반영한다.
- 결제 실패, 환불 요청, 보상 쿠폰 같은 주변 맥락은 현재 목업 데이터만으로 충분히 조합 가능하다.

## 범위

- 구독 운영 helper 추가 또는 분리
- `/admin/subscriptions` 워크벤치 강화
- 상태 변경 사유 입력 및 validation
- 상태별 위험 안내와 확인 패널 강화
- 최근 결제 / 환불 / 쿠폰 컨텍스트 카드 추가
- 관련 테스트 추가/갱신

## 구현 단계

1. 구독 운영 도메인 helper 정리
   - 선택된 구독의 관련 결제/환불/쿠폰 맥락 조합
   - 상태 전환 metadata와 validation 규칙 분리
2. 워크벤치 UI 강화
   - 상태 전환 사유 textarea
   - validation 실패 피드백
   - 상태별 안내 문구와 후속 조치 메시지
   - 결제/환불/쿠폰 요약 패널 추가
3. 클라이언트 상호작용 다듬기
   - `startTransition`을 사용해 비긴급 업데이트를 분리
   - 선택 상태와 필터 상태가 어긋나지 않도록 안전 처리
4. 테스트 및 검증
   - 사유 입력 validation
   - 상태 변경 후 context 및 activity 반영
   - 전체 검증 명령 실행

## 리스크

- 화면에 너무 많은 운영 정보가 한 번에 들어가면 복잡해질 수 있다.
  - 좌측은 상태 전환, 우측은 운영 컨텍스트라는 역할 분리로 정보 밀도를 통제한다.
- validation 규칙이 과하면 데모 흐름이 답답해질 수 있다.
  - 모든 상태 전환을 막기보다, 사유 입력과 경고 피드백 중심의 soft guardrail을 우선 적용한다.
- 여러 도메인 데이터를 함께 보여주면서 렌더링 코드가 비대해질 수 있다.
  - 조합 로직은 helper로 옮기고 view는 렌더링과 이벤트 처리 중심으로 유지한다.

## 검증 방법

- 사유 없이 상태 변경을 확정하려 할 때 실패 피드백이 보이는지 확인한다.
- 사유를 입력한 뒤 상태 변경이 성공하고 activity feed에 사유가 남는지 확인한다.
- 선택한 구독에 연결된 결제 / 환불 / 쿠폰 컨텍스트가 올바르게 보이는지 확인한다.
- `npm.cmd run lint`
- `npm.cmd run typecheck`
- `npm.cmd run test`
- `npm.cmd run build`
