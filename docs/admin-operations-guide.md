# Subscription Ops Console 운영자 사용 가이드

## 문서 목적

이 문서는 현재 저장소에 구현된 **Subscription Ops Console**을 기준으로,

- 운영자가 어떤 화면을 어떤 순서로 사용하는지
- 어떤 운영 흐름이 구현되어 있는지
- 각 역할이 어디까지 접근할 수 있는지

를 빠르게 이해할 수 있도록 정리한 안내서입니다.

이 프로젝트는 현재 **mock/local data 기반의 프론트엔드 제품**입니다.  
즉, 실제 결제사나 백엔드와 연결된 운영 도구는 아니지만, 실제 구독 서비스 운영 콘솔처럼 보이도록 주요 업무 흐름을 재현하고 있습니다.

## 제품 개요

Subscription Ops Console은 두 영역으로 구성됩니다.

- 고객용 영역
  - 랜딩 페이지
  - 요금제 비교
  - 체크아웃 목업
  - 내 구독
  - 결제 내역
- 관리자용 영역
  - 운영 개요
  - 고객 관리
  - 구독 상태 운영
  - 결제 대응
  - 환불 검토
  - 쿠폰 운영
  - 분석 대시보드
  - 관리자 권한/역할
  - 감사 로그

운영 관점에서 이 제품의 핵심은 다음입니다.

- 고객, 구독, 결제, 환불, 쿠폰, 관리자, 감사 로그를 하나의 흐름으로 연결
- 위험한 액션에 대해 확인 절차와 피드백 제공
- 상태 배지, 활동 로그, 관련 화면 quick link로 실제 운영 흐름 재현
- 빈 상태, 에러 상태, 로딩 상태를 화면 단위로 고려

## 관리자 진입 방법

관리자 화면은 `/admin` 이하에서 동작합니다.

주요 관리자 라우트는 다음과 같습니다.

- `/admin`
- `/admin/customers`
- `/admin/customers/[customerId]`
- `/admin/subscriptions`
- `/admin/payments`
- `/admin/payments/[paymentId]`
- `/admin/refunds`
- `/admin/refunds/[refundId]`
- `/admin/coupons`
- `/admin/analytics`
- `/admin/admin-users`
- `/admin/audit-log`

관리자 레이아웃에는 다음 기능이 포함되어 있습니다.

- 좌측 사이드바 네비게이션
- 상단 현재 관리자 세션 표시
- 역할 배지 표시
- 현재 라우트 접근 가능 여부 표시
- mock session 전환 버튼
- 테마 전환 버튼

## Mock Session과 역할 전환

이 프로젝트는 실제 로그인 대신 **mock session** 방식으로 관리자 역할을 전환합니다.

관리자 화면 상단에서 다른 관리자 버튼을 누르면 같은 화면을 다른 역할로 다시 볼 수 있습니다.  
이 방식으로 역할별 접근 차이를 시뮬레이션합니다.

현재 역할 개념은 다음과 같습니다.

- `viewer`
- `support`
- `billing_manager`
- `ops_admin`

역할에 따라 접근 가능한 관리자 화면이 다르며, 접근할 수 없는 화면에서는 다음 동작이 일어납니다.

- 해당 화면 본문 대신 차단 메시지 표시
- 현재 역할로 접근 가능한 대체 화면 링크 제공

즉, 이 프로젝트는 **UI 수준의 역할 기반 접근 제어 흐름**을 이미 포함하고 있습니다.

## 운영 흐름 개요

관리자 입장에서의 대표 운영 흐름은 아래와 같습니다.

1. `/admin`에서 오늘 우선순위와 watchlist를 확인한다.
2. `/admin/customers`에서 특정 고객을 검색해 상세로 진입한다.
3. 고객 상세에서 구독, 결제, 환불, 쿠폰, 감사 이력을 종합 확인한다.
4. 필요 시 `/admin/subscriptions`로 이동해 구독 상태를 변경한다.
5. 결제 문제가 있으면 `/admin/payments`에서 실패 결제를 처리한다.
6. 환불 요청이 있으면 `/admin/refunds`에서 승인 또는 반려를 진행한다.
7. 보상이나 프로모션이 필요하면 `/admin/coupons`에서 쿠폰을 발급하거나 회수한다.
8. 운영 현황은 `/admin/analytics`에서 확인하고, 모든 변경 이력은 `/admin/audit-log`에서 추적한다.

## 화면별 사용 방법

### 1. 운영 개요 `/admin`

운영 개요 화면은 하루 업무의 시작점입니다.

여기서 볼 수 있는 정보:

- KPI 카드
- 우선 처리 큐
- 빠른 이동 링크
- watchlist
- 최근 운영 활동

추천 사용 방식:

1. 우선 처리 큐에서 오늘 먼저 볼 영역을 확인합니다.
2. watchlist에서 위험 고객이나 이슈 건을 확인합니다.
3. 빠른 이동 링크로 고객/결제/환불/분석 화면으로 이동합니다.

### 2. 고객 목록 `/admin/customers`

고객 목록은 운영 탐색의 기본 진입점입니다.

지원 기능:

- 검색
- 구독 상태 필터
- 플랜 필터
- 정렬
- 페이지네이션

추천 사용 방식:

1. 고객 이름, 이메일, 회사명으로 검색합니다.
2. 상태나 플랜 조건으로 운영 대상만 좁힙니다.
3. 고객 상세로 들어가 해당 계정의 운영 맥락을 확인합니다.
4. 필요하면 구독 운영 화면으로 이동합니다.

### 3. 고객 상세 `/admin/customers/[customerId]`

고객 상세는 한 고객에 대한 운영 맥락을 모아서 보는 화면입니다.

확인 가능한 정보:

- 고객 프로필
- 현재 구독 요약
- 결제 이력
- 환불 이력
- 쿠폰 이력
- 감사 이벤트

추천 사용 방식:

1. 고객의 현재 플랜과 구독 상태를 먼저 확인합니다.
2. 최근 결제 실패나 환불 요청이 있는지 봅니다.
3. 보상용 쿠폰이 이미 발급돼 있는지 확인합니다.
4. 관련 quick link로 결제 상세, 환불 상세, 구독 워크벤치로 이동합니다.

### 4. 구독 상태 워크벤치 `/admin/subscriptions`

이 화면은 실제 운영 업무에 가장 가까운 핵심 화면 중 하나입니다.

지원 기능:

- 구독 검색
- 상태 필터
- 플랜 필터
- 정렬
- 페이지네이션
- 선택된 구독의 상태 전환
- 상태 변경 사유 입력
- 확인 절차
- 성공/실패 피드백
- 관련 결제/환불/쿠폰 컨텍스트 확인
- 변경 활동 로그

추천 사용 방식:

1. 구독을 검색하거나 테이블에서 선택합니다.
2. 현재 상태와 리스크 배지를 확인합니다.
3. 가능한 전환 옵션 중 하나를 고릅니다.
4. 변경 사유를 입력합니다.
5. 확인 후 상태를 변경합니다.
6. 즉시 반영된 피드백과 활동 로그를 확인합니다.

이 화면은 단순 상태 변경이 아니라, 구독과 연결된 결제/환불/쿠폰 맥락까지 함께 보여주도록 설계되어 있습니다.

### 5. 결제 대응 `/admin/payments`

이 화면은 실패 결제나 미해결 결제 건을 운영자가 후속 처리하는 공간입니다.

지원 기능:

- 실패/보류 결제 우선 노출
- 선택 결제의 상태 조정
- 결제 상세 이동
- 고객 상세 이동
- 활동 로그 기록

추천 사용 방식:

1. 실패 또는 pending 결제를 우선 확인합니다.
2. 고객 맥락과 결제 수단을 확인합니다.
3. 상황에 따라 다음 중 하나를 선택합니다.
   - pending으로 되돌리기
   - 수동으로 paid 처리
   - failed 상태 유지
4. 확인 후 결과를 활동 로그에서 확인합니다.

### 6. 결제 상세 `/admin/payments/[paymentId]`

결제 상세는 하나의 결제 건을 깊게 보는 화면입니다.

확인 가능한 정보:

- 결제 상태
- 금액
- 시도 시점
- 인보이스 정보
- 관련 고객
- 관련 구독
- 관련 환불
- 감사 이력

추천 사용 방식:

1. 결제 상태와 인보이스 번호를 확인합니다.
2. 관련 고객/구독으로 연결해서 운영 맥락을 넓혀 봅니다.
3. 환불 이력이 있다면 환불 상세로 이동합니다.

### 7. 환불 검토 보드 `/admin/refunds`

이 화면은 환불 요청을 승인/반려하는 운영 보드입니다.

지원 기능:

- 환불 목록 확인
- 검토 대상 선택
- 승인 또는 반려 준비
- 검토 메모 입력
- 확인 절차
- 처리 결과 활동 로그

추천 사용 방식:

1. 요청 상태의 환불 건을 선택합니다.
2. 결제와 고객 정보를 함께 확인합니다.
3. 검토 메모를 입력합니다.
4. 승인 또는 반려를 선택합니다.
5. 최종 확인 후 처리합니다.

이 흐름은 실제 운영팀의 “검토 메모 + 결정 + 로그” 구조를 반영합니다.

### 8. 환불 상세 `/admin/refunds/[refundId]`

환불 상세는 환불 요청 한 건을 깊게 확인하는 화면입니다.

확인 가능한 정보:

- 환불 상태
- 환불 금액
- 요청 사유
- 검토 메모
- 검토 완료 시점
- 관련 고객/결제/구독
- 감사 이력

추천 사용 방식:

1. 요청 사유와 검토 메모를 확인합니다.
2. 관련 결제 상세와 고객 상세로 이동합니다.
3. 필요하면 구독 워크벤치까지 이어서 운영합니다.

### 9. 쿠폰 운영 `/admin/coupons`

이 화면은 보상/프로모션 쿠폰을 발급하고 회수하는 공간입니다.

지원 기능:

- 검색
- 상태 필터
- 정렬
- 페이지네이션
- 새 쿠폰 발급 폼
- 대상 고객 지정
- 할인 유형/값 입력
- 만료일 설정
- 쿠폰 회수
- 처리 로그

추천 사용 방식:

1. 특정 고객에게 보상 쿠폰이 필요한지 확인합니다.
2. 발급 폼에서 제목, 코드, 대상 고객, 할인 조건, 만료일을 입력합니다.
3. 발급 후 목록과 상세 패널에서 상태를 확인합니다.
4. 더 이상 유효하지 않아야 하면 회수 절차를 진행합니다.

### 10. 분석 대시보드 `/admin/analytics`

분석 화면은 운영 인사이트를 빠르게 보는 곳입니다.

확인 가능한 정보:

- KPI 카드
- MRR/활성 고객/실패 결제 추이
- 구독 상태 분포
- 플랜 분포
- 고객 세그먼트 분포
- 리스크 큐

추천 사용 방식:

1. 오늘 운영 이상 징후가 있는지 headline KPI를 확인합니다.
2. 추이 차트로 성장/리스크 방향을 봅니다.
3. 리스크 큐에서 바로 필요한 화면으로 이동합니다.

### 11. 관리자 권한 관리 `/admin/admin-users`

이 화면은 현재 mock session 기반 권한 구조를 설명하는 관리자 안내 화면입니다.

확인 가능한 정보:

- 역할별 요약
- 역할별 접근 범위
- 관리자 디렉터리
- 라우트 접근 매트릭스

추천 사용 방식:

1. 어떤 역할이 어떤 화면에 접근 가능한지 확인합니다.
2. mock session으로 역할을 바꿔 실제 차단/허용 동작을 검증합니다.
3. 운영 문서나 데모 설명 시 권한 구조를 보여주는 화면으로 활용합니다.

### 12. 감사 로그 `/admin/audit-log`

감사 로그는 운영 변경 이력을 추적하는 화면입니다.

지원 기능:

- actor 필터
- entity 필터
- 이벤트 요약 카드
- 관련 화면 링크
- 최근 타임라인

추천 사용 방식:

1. 특정 관리자(actor) 기준으로 필터링합니다.
2. customer/subscription/payment/refund/coupon 단위로 좁혀 봅니다.
3. 이벤트 상세와 연결 링크로 실제 대상 화면으로 이동합니다.

## 대표 운영 시나리오

### 시나리오 1. 결제 실패 후 구독 상태 확인

1. `/admin`에서 우선 처리 큐 또는 watchlist를 확인합니다.
2. `/admin/payments`에서 실패 결제를 선택합니다.
3. 결제 상태를 검토하고 필요 시 pending 또는 paid로 조정합니다.
4. 결제 상세로 이동해 고객/구독 맥락을 확인합니다.
5. 필요하면 `/admin/subscriptions`로 이동해 구독 상태를 조정합니다.

### 시나리오 2. 고객 불만에 따른 보상 처리

1. `/admin/customers`에서 고객을 검색합니다.
2. 고객 상세에서 결제 실패나 환불 이력, 현재 쿠폰 여부를 확인합니다.
3. `/admin/coupons`에서 보상 쿠폰을 발급합니다.
4. 발급 후 고객 상세에서 쿠폰 이력을 다시 확인합니다.
5. 필요하면 감사 로그에서 누가 어떤 조치를 했는지 추적합니다.

### 시나리오 3. 환불 요청 검토

1. `/admin/refunds`에서 요청 상태 환불을 선택합니다.
2. 고객, 결제, 환불 사유를 확인합니다.
3. 검토 메모를 입력합니다.
4. 승인 또는 반려를 확정합니다.
5. 환불 상세와 감사 로그에서 처리 결과를 검증합니다.

### 시나리오 4. 역할별 접근 검증

1. 관리자 화면 상단의 mock session 버튼으로 역할을 전환합니다.
2. `/admin/admin-users`에서 역할별 접근 범위를 확인합니다.
3. 권한이 없는 라우트에 진입해 차단 화면이 정상 표시되는지 확인합니다.
4. 허용된 대체 링크가 노출되는지 확인합니다.

## 고객용 흐름과 관리자용 흐름의 연결

이 프로젝트는 고객용 화면과 관리자용 화면이 분리되어 있지만, 같은 도메인 데이터를 공유하도록 설계되어 있습니다.

예를 들면:

- 고객이 `/checkout`에서 주문을 완료한 뒤
- `/app/subscription`, `/app/billing`에서 상태를 보게 되고
- 관리자는 `/admin/customers`, `/admin/payments`, `/admin/subscriptions`에서 같은 흐름을 운영 관점으로 추적하게 됩니다.

즉, 이 프로젝트의 강점은 단순 관리자 화면 모음이 아니라,

- 고객 여정
- 운영자의 후속 조치
- 변경 이력 추적

이 하나의 시나리오로 연결된다는 점입니다.

## 현재 프로젝트의 한계

현재 구현은 운영 흐름 중심의 프론트엔드 제품이며, 다음 제약이 있습니다.

- 실제 인증/인가 백엔드 없음
- 실제 데이터베이스 없음
- 실제 결제 연동 없음
- 실제 서버 액션이나 API mutation 없음
- 대부분의 상태 변경은 클라이언트 로컬 상태 기반
- 감사 로그도 mock data 및 화면 내 activity feed 중심

따라서 이 프로젝트는 다음 용도에 특히 적합합니다.

- 운영 콘솔 IA/UX 시연
- 관리자 워크플로우 설계 검토
- 프론트엔드 구조/도메인 모델 설계 기반 만들기
- 이후 API 연결 전 단계의 제품 프로토타이핑

## 추천 다음 단계

이 프로젝트를 다음 단계로 발전시키려면 아래 순서를 추천합니다.

1. 서버 데이터 경계 정의
2. 관리자 인증과 실제 역할 기반 접근 제어 연결
3. 구독/결제/환불 mutation을 서버 액션 또는 API로 이동
4. 감사 로그를 실제 이벤트 저장 구조로 전환
5. 검색/필터를 URL 상태 및 서버 데이터 조회와 연결
6. E2E 테스트 추가

## 요약

현재 Subscription Ops Console은 다음을 설명하고 시연하기에 충분한 상태입니다.

- 구독 서비스 운영팀이 어떤 화면을 사용해 업무를 처리하는지
- 고객, 구독, 결제, 환불, 쿠폰이 어떻게 연결되는지
- 관리자 역할에 따라 접근 범위가 어떻게 달라지는지
- 변경 이력을 어떻게 추적할 수 있는지

즉, 이 프로젝트는 **“구독 서비스 운영 콘솔의 현실적인 업무 흐름을 보여주는 프론트엔드 제품”**으로 이해하면 가장 정확합니다.
